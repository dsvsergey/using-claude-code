Claude Code для команди

Короткий практичний гайд: як налаштувати, як не спалювати токени, як зберігати знання про проєкт локально і як працювати так, щоб результат був передбачуваним.

⚙️ налаштування🧠 база знань💸 токени📐 spec-driven✅ практики

1. Швидкий старт

  1. Встановіть Claude Code (див. офіційну документацію — docs.claude.com).
  2. Відкрийте термінал у корені репозиторію і запустіть claude.
  3. Виконайте /init — Claude проаналізує код і створить стартовий CLAUDE.md. Відредагуйте його вручну: прибрати воду, додати те, чого не видно з коду.
  4. Закомітьте CLAUDE.md, .claude/settings.json та .mcp.json — тоді вся команда стартує з однаковою конфігурацією.
cd my-repo
claude          # інтерактивна сесія
/init           # згенерувати CLAUDE.md
/status         # перевірити модель, акаунт, налаштування

2. CLAUDE.md — памʼять проєкту

CLAUDE.md завантажується в контекст кожної сесії. Тому він має бути коротким і щільним: кожен рядок коштує токенів у кожному запиті.

Де лежить

~/.claude/CLAUDE.mdособисті правила для всіх проєктів
./CLAUDE.mdправила проєкту, в git, для всієї команди
./CLAUDE.local.mdособисті правила для проєкту (в .gitignore)
./subdir/CLAUDE.mdпідвантажується, коли Claude працює в цій папці

Що писати

  • Команди: build, test, lint, запуск одного тесту.
  • Архітектурні межі: «UI не ходить напряму в БД».
  • Конвенції, які не видно з коду.
  • Пастки: «міграції тільки через …», «не чіпати legacy/».
  • Посилання на детальні документи через @docs/file.md замість копіювання тексту.

Чого не писати

  • Опис структури папок, який Claude і так бачить.
  • Загальні поради («пиши чистий код»).
  • Секрети, токени, паролі.
Приклад CLAUDE.md 
# Project: billing-api

## Commands
- Install: `pnpm i`
- Test all: `pnpm test` · one file: `pnpm vitest run path/to/file.test.ts`
- Lint+types: `pnpm lint && pnpm typecheck` (run before saying "done")

## Architecture
- `src/domain` — pure logic, no IO. `src/infra` — DB/HTTP adapters.
- All DB access via repositories in `src/infra/repos`. Never import prisma elsewhere.

## Conventions
- Errors: return `Result<T, AppError>`, never throw in domain.
- New endpoint = handler + zod schema + test in `tests/api`.

## Gotchas
- Money is integer cents. Never use float.
- `legacy/` is frozen — do not modify.

## More docs
- @docs/architecture.md
- @docs/release-process.md

💡 Порада: під час роботи кажіть «додай це в CLAUDE.md», коли Claude помилився через незнання конвенції. Так файл росте з реальних проблем, а не з вигаданих правил. Раз на місяць чистіть його.

3. settings.json і дозволи

~/.claude/settings.jsonкористувацькі налаштування
.claude/settings.jsonпроєктні, в git — спільні для команди
.claude/settings.local.jsonособисті для проєкту, не комітяться

Дозволи знімають постійні запити «Allow?» для безпечних команд і забороняють небезпечні. Керувати можна командою /permissions або вручну:

{
  "permissions": {
    "allow": [
      "Bash(pnpm test:*)",
      "Bash(pnpm lint:*)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(git log:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(git push:*)",
      "Bash(rm -rf:*)"
    ]
  }
}

⚠️ Не вмикайте режим «пропускати всі дозволи» на робочій машині з доступом до прод-секретів. Якщо потрібна повна автономія — запускайте в контейнері / devcontainer.

4. Спільна конфігурація команди

Ідея: все, що робить Claude «розумним» у вашому проєкті, лежить у репозиторії і проходить code review, як звичайний код.

repo/
├── CLAUDE.md                 # правила проєкту
├── .mcp.json                 # спільні MCP-сервери (без секретів!)
├── .claude/
│   ├── settings.json         # дозволи, hooks
│   ├── commands/             # власні /slash-команди команди
│   │   └── review-pr.md
│   ├── agents/               # спеціалізовані subagents
│   │   └── test-writer.md
│   └── skills/               # skills з інструкціями та скриптами
│       └── release/SKILL.md
├── docs/                     # детальна документація, на яку посилається CLAUDE.md
└── specs/                    # специфікації (Spec Kit)
  • Секрети для MCP — через змінні оточення (${API_KEY} у .mcp.json), а не в файлі.
  • Зміни в CLAUDE.md і .claude/ — через PR, як і код.
  • Для набору спільних інструментів між репозиторіями — оформіть plugin і внутрішній marketplace (/plugin).

5. Економія токенів і контексту

Головне правило: контекст — найдорожчий ресурс. Чим він більший і «брудніший», тим дорожче і гірше працює модель.

Звички

  • /clear між незалежними задачами. Одна сесія = одна задача.
  • /compact з підказкою, що зберегти: /compact залиш план і список змінених файлів.
  • /context — подивитись, що займає контекст (MCP-тули, файли памʼяті тощо).
  • Давайте точні шляхи: @src/billing/invoice.ts замість «знайди, де рахунки».
  • Великі дослідження («пройдись по всьому репо») — через subagent: він читає файли у своєму контексті й повертає тільки висновок.
  • Вимикайте MCP-сервери, які не потрібні в цьому проєкті — опис кожного тула займає контекст.
  • Не вставляйте величезні логи — давайте хвіст або фільтр (| tail -50, grep ERROR).

Вибір моделі

  • /model — перемикання. Потужна модель — для планування й складних задач, швидша/дешевша — для рутини.
  • Для subagents можна задати окрему, дешевшу модель у їхньому frontmatter.

Вимірювання

  • /cost або /usage — витрати поточної сесії / ліміти.
  • ccusage — аналіз локальних логів Claude Code: витрати по днях і сесіях.
  • Statusline (/statusline) — показувати заповненість контексту прямо в терміналі.

💡 Локальна база знань економить токени не «магічно», а тому, що Claude отримує маленький точний фрагмент (вузол графа, нотатку, сигнатуру функції) замість читання десятків файлів. Ефект найбільший на великих репозиторіях і повторюваних питаннях.

6. Локальна база знань: тули

Три різні задачі — три типи інструментів. Не ставте все одразу: почніть з 1–2 і подивіться на /context і /cost.

Карта коду (що де лежить і як повʼязано)

graphify

Будує граф знань (код, документи) у graphify-out/. Запити graphify query, path, explain повертають маленький підграф замість сирого grep.

Коли: великий/незнайомий репозиторій, питання про архітектуру. Після змін — graphify update .

Serena (MCP)

Семантична навігація по коду через LSP: знайти символ, посилання, редагувати на рівні функцій — без читання цілих файлів.

Коли: типізовані мови, великі файли, рефакторинг.

Памʼять між сесіями (рішення, баги, домовленості)

Вбудована памʼять: CLAUDE.md

Найпростіший і найпрозоріший варіант: текст у git, видно в review. /memory — відкрити для редагування.

Коли: завжди. Це база.

engram (MCP)

Локальна памʼять (SQLite + пошук): Claude зберігає рішення, причини багів, конвенції і шукає їх у наступних сесіях.

Коли: довгі проєкти, багато сесій. Мінус: памʼять особиста, не в git — важливе переносьте в CLAUDE.md/docs.

docs/ + ADR у репозиторії

Architecture Decision Records у docs/adr/, на які посилається CLAUDE.md через @. Спільно для людей і для Claude.

Коли: командні рішення, які мають пережити людей.

Актуальна документація бібліотек

Context7 (MCP)

Підтягує свіжу документацію конкретної версії бібліотеки замість «памʼяті» моделі. Менше вигаданих API — менше ітерацій виправлень.

Коли: фреймворки, що швидко змінюються.

Приклад спільного .mcp.json 
{
  "mcpServers": {
    "context7": {
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp"]
    }
  }
}

Перевіряйте актуальні команди встановлення в README кожного інструмента. Додати сервер можна і командою claude mcp add; переглянути стан — /mcp.

7. Spec-driven development: Spec Kit (specify)

GitHub Spec Kit — спочатку специфікація, потім план, потім задачі, потім код. Для Claude це означає: менше вгадувань, менше переписувань, і артефакти, які можна рецензувати.

/speckit-constitutionпринципи проєкту (якість, тести, стек)
/speckit-specifyЩО і НАВІЩО — без технологій
/speckit-clarifyзакрити неоднозначності
/speckit-planЯК — стек, архітектура, контракти
/speckit-tasksрозбивка на задачі
/speckit-implementреалізація по задачах
specify init --here --integration claude   # ініціалізувати в існуючому репо
specify check                # перевірити оточення

Нові версії Spec Kit ставлять команди як skills у .claude/skills/ з дефісом (/speckit-plan); старі — у .claude/commands/ з крапкою (/speckit.plan). Є також /speckit-converge — оцінити код і дописати залишок роботи в задачі.

Поради

  • Рецензуйте spec.md і plan.md у PR до реалізації — це найдешевше місце знайти помилку.
  • Не використовуйте для дрібних фіксів — overhead більший за користь.
  • Між етапами робіть /clear: артефакти лежать у файлах, контекст можна не тягнути.

Альтернативи / доповнення

  • Plan mode (Shift+Tab) — вбудований «легкий» варіант: Claude досліджує і пропонує план, нічого не змінюючи.
  • Superpowers (plugin) — набір skills для дисципліни: brainstorming → plan → TDD → review.

8. Робочий цикл задачі

  1. Дослідити. «Прочитай модуль X і поясни, як працює Y. Код не змінюй.»
  2. Спланувати. Plan mode або Spec Kit. Перевірити план очима.
  3. Тести спочатку. «Напиши тест, що відтворює баг. Переконайся, що він падає.»
  4. Реалізувати малими кроками, кожен крок перевіряється тестом / лінтером.
  5. Перевірити. Попросіть запустити тести, лінт, типи. Для UI — скріншот.
  6. Review. /review або окремий subagent-рецензент, потім людина.
  7. Зафіксувати знання. Нова конвенція → CLAUDE.md. Рішення → ADR.

💡 Дайте Claude спосіб перевірити себе (тести, лінтер, скріншот) — це найбільше підвищує якість результату.

9. Skills, subagents, hooks, MCP — що коли

МеханізмДля чогоПриклад
Slash command
.claude/commands/*.md		Повторюваний промпт, який запускає людина/review-pr 123, /fix-issue
Skill
.claude/skills/*/SKILL.md		Інструкції + скрипти, які Claude підвантажує сам, коли задача підходить. В контексті лише короткий опис, поки skill не потрібен.«як робити реліз», «як писати міграцію»
Subagent
.claude/agents/*.md		Окремий контекст для ізольованої задачі; повертає лише результатcode-reviewer, test-writer, дослідник репо
Hook
settings.json		Детерміновані дії на події — виконує harness, а не модельформатувати після Edit, блокувати запис у .env
MCP
.mcp.json		Доступ до зовнішніх систем і данихJira/Linear, БД, документація, браузер
Приклад hook: автоформатування після редагування 
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npx prettier --write \"$CLAUDE_PROJECT_DIR\" --log-level silent || true" }
        ]
      }
    ]
  }
}

Правило: якщо щось має відбуватися завжди — це hook, а не прохання в CLAUDE.md.

Приклад subagent: .claude/agents/code-reviewer.md 
---
name: code-reviewer
description: Reviews the current diff for bugs, security and convention violations. Use after implementing a change.
tools: Read, Grep, Glob, Bash
---
You are a strict reviewer. Run `git diff`, read CLAUDE.md conventions,
report only real issues with file:line and a concrete fix. No style nitpicks.

10. Кращі практики

Промпти

  • Конкретика: файл, функція, очікувана поведінка, критерій «готово».
  • Кажіть, чого не робити: «не змінюй публічний API».
  • Скріншоти, логи помилок, приклади вхід/вихід — вставляйте прямо в чат.
  • Для складного — попросіть спочатку план, потім код.
  • Зупиняйте рано: Esc — перервати, EscEsc / /rewind — відкотитись.

Git

  • Окрема гілка на задачу; часті маленькі коміти — легко відкотити.
  • Паралельні задачі — через git worktree, по сесії Claude на кожен.
  • Не дозволяйте git push без підтвердження.

Якість і безпека

  • Код від Claude проходить той самий review, що й код людини. Автор PR відповідає за нього.
  • Секрети — у deny, ніколи в CLAUDE.md чи .mcp.json.
  • Довіряйте MCP-серверам і plugins лише з перевірених джерел — вони виконують код на вашій машині.
  • Перевіряйте «впевнені» твердження про API — через тести або Context7.

Команда

  • Діліться вдалими промптами як slash-командами в репо.
  • Раз на спринт — 15 хв «що спрацювало / що ні з Claude» → оновити CLAUDE.md і цей гайд.
  • Автоматизація в CI: claude -p "…" (headless) або GitHub Action для review PR.

13. Автоналаштування (setup-kit)

Усе з цього гайду можна застосувати однією командою. За замовчуванням налаштування глобальні — у ~/.claude, для всіх сесій і проєктів; конкретний репозиторій налаштовується лише з --project <path>. Скрипт нічого не перезаписує: наявні файли пропускає, JSON зливає, перед зміною робить .bak.

# macOS / Linux
./setup-kit/setup.sh --dry-run            # що буде змінено
./setup-kit/setup.sh --preset minimal     # глобально: Claude, deny для секретів, context7
./setup-kit/setup.sh --preset full        # + правила в ~/.claude/CLAUDE.md, agents, Serena, graphify, Spec Kit, engram, statusline
./setup-kit/setup.sh --project ~/code/app # каркас CLAUDE.md і дозволи для репозиторію
./setup-kit/setup.sh doctor               # перевірка

# Windows (PowerShell, у т.ч. RDP)
powershell -ExecutionPolicy Bypass -File .\setup-kit\setup.ps1 --preset minimal
ПрапорецьЩо робить
(без прапорців) / --project <path>глобально (~/.claude) / лише репозиторій; разом — --user --project <path>
--with a,b / --without c,dдодати / прибрати компоненти
--yesбез запитань (для масового розгортання)
--dry-runпоказати diff, нічого не змінювати

💡 Після запуску: claude → /login → /status → /mcp, Для репозиторію: заповніть каркас CLAUDE.md, потім закомітьте CLAUDE.md і .claude/.

Повний список компонентів — у setup-kit/README.md.

Гайд живий: пропонуйте зміни через PR. Перевіряйте деталі в офіційній документації Claude Code — продукт швидко оновлюється.
